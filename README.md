# Agri Funds Tracker

Web app for tracking investor fund flow in an agriculture investment platform, settled on the **Stellar testnet**.

```
Investor wallet  ──▶  Central Treasury  ──▶  Project allocation  ──▶  Farmer payout
```

## Stack

- **Backend**: Node.js + Express, MongoDB (Mongoose), `stellar-sdk` for real **testnet** payments. JWT auth, AES-256-GCM encryption of wallet seeds at rest, SSE for live updates.
- **Frontend**: React + Vite (PWA), Recharts.
- **Asset**: XLM on Stellar **testnet** (Friendbot-funded). There is **no mainnet support** — the server refuses to start against a mainnet Horizon.

## Local development

Two terminals.

**Terminal 1 — backend** (port 4000):
```bash
cd backend
cp .env.example .env      # then fill in the values (see "Environment variables")
npm install
npm start
```

**Terminal 2 — frontend** (port 5173, Vite proxies `/api` → 4000):
```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. Locally `VITE_API_BASE_URL` is left empty so the Vite dev proxy handles `/api`.

## Production deployment

The app is deployed as two services: the **backend on Render** and the **frontend on Vercel**. All secrets are read from environment variables — no `.env` file is needed at runtime.

### 1. Backend on Render

The repo ships [`render.yaml`](./render.yaml) (Render Blueprint). Easiest path:

1. In Render, **New → Blueprint**, point it at this repo. Render reads `render.yaml` and creates the `agri-funds-api` web service (root dir `backend`, `npm install` / `npm start`, health check `/api/health`).
2. Set the env vars marked `sync: false` in the Render dashboard (see table below). `JWT_SECRET` is auto-generated by Render.
3. Deploy. The health check at `/api/health` returns `200` once MongoDB is connected.

Manual setup (no Blueprint) — create a **Web Service** with:
- **Root Directory**: `backend`
- **Build Command**: `npm install`
- **Start Command**: `npm start`
- **Health Check Path**: `/api/health`

**Render environment variables**

| Variable | Required | Notes |
|---|---|---|
| `NODE_ENV` | yes | `production` |
| `MONGODB_URI` | yes | MongoDB Atlas connection string |
| `JWT_SECRET` | yes | Long random string. Render can auto-generate (`generateValue: true`) |
| `WALLET_ENC_KEY` | yes | 64-char hex (32 bytes). `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Must differ from `JWT_SECRET` |
| `ADMIN_EMAIL` | yes | Email for the seeded admin login |
| `ADMIN_PASSWORD` | yes | Admin password. **Required in production** — the server refuses to seed a default-credential admin |
| `CORS_ORIGIN` | yes | Comma-separated Vercel origin(s), no trailing slash, e.g. `https://agri-funds.vercel.app` |
| `CORS_ALLOW_VERCEL_PREVIEWS` | no | `true` to also allow any `https://*.vercel.app` preview URL |
| `JWT_EXPIRES_IN` | no | Access-token lifetime. Default `1d` |
| `STELLAR_HORIZON_URL` | no | Defaults to testnet. **Mainnet (`horizon.stellar.org`/pubnet) is rejected at boot** |
| `STELLAR_FRIENDBOT_ENABLED` | no | Default `true`. Set `false` to disable the testnet faucet |
| `STELLAR_FRIENDBOT_TIMEOUT_MS` | no | Friendbot timeout in ms. Default `30000` |
| `SEP10_SERVER_SECRET` | no | Enables non-custodial wallet login (SEP-10). Stellar secret seed (`S...`), **testnet only**, distinct from any wallet keys. Unset = wallet login disabled |
| `SEP10_HOME_DOMAIN` | no | Label embedded in SEP-10 challenges. Default `agri-funds.testnet` |
| `SEED_DEMO_USERS` | no | Leave `false` in production |
| `MONEY_RATE_LIMIT_MAX` | no | Max money-moving requests (invest/allocate/fund/payout/distribution) per client per minute. Default `30` |
| `WALLET_AUTH_RATE_LIMIT_MAX` | no | Max SEP-10 wallet auth attempts per client per 15 min. Default `20` |
| `PORT` | no | Injected by Render automatically |

The server validates this configuration at startup and **exits with a clear error** if anything required is missing or malformed (e.g. a non-hex `WALLET_ENC_KEY`, or a mainnet Horizon URL).

### 2. Frontend on Vercel

The repo ships [`frontend/vercel.json`](./frontend/vercel.json) (Vite framework preset).

1. In Vercel, **Add New → Project**, import this repo.
2. Set **Root Directory** to `frontend`.
3. Build settings are inferred from `vercel.json` (`npm run build` → `dist`).
4. Add the env var below, then deploy.

**Vercel environment variables**

| Variable | Required | Notes |
|---|---|---|
| `VITE_API_BASE_URL` | yes | Your Render API origin, **no trailing slash**, e.g. `https://agri-funds-api.onrender.com`. Baked in at build time — set it for the Production (and Preview) environments and redeploy after changes |

The frontend never hardcodes `localhost`; it reads `VITE_API_BASE_URL` for both REST calls and the SSE stream.

### 3. Wire the two together

1. Deploy the backend first; note its Render URL (e.g. `https://agri-funds-api.onrender.com`).
2. Set `VITE_API_BASE_URL` on Vercel to that URL and deploy the frontend; note the Vercel URL (e.g. `https://agri-funds.vercel.app`).
3. Set `CORS_ORIGIN` on Render to the Vercel URL and redeploy the backend.
4. Visit the Vercel URL and sign in with `ADMIN_EMAIL` / `ADMIN_PASSWORD`.

### Live updates (SSE)

The frontend opens an `EventSource` straight to the Render API (`<VITE_API_BASE_URL>/api/events`). The connection is authenticated with a short-lived ticket (EventSource can't send `Authorization` headers), and the server sends `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`, and a 25s heartbeat so the stream survives proxies and idle periods. No Vercel-side proxying is involved, so there's nothing extra to configure.

## Testnet & Friendbot notes

- Every transaction is signed with the **testnet** network passphrase, and the Horizon URL is validated at boot — the app cannot move real (mainnet) funds.
- **Friendbot** is the testnet faucet used to fund new wallets (treasury, each new investor, and each new **farmer**). It is testnet-only, time-boxed (so a flaky faucet can't hang a request), and can be turned off with `STELLAR_FRIENDBOT_ENABLED=false`.
- **End-to-end on-chain money flow (testnet):** investor → treasury (real payment), treasury → project (internal allocation book-keeping, projects have no wallet), and **treasury → farmer payout is a real on-chain XLM transfer**. Farmers get an auto-provisioned, Friendbot-funded **custodial** testnet wallet on creation (mirrors investors), so payouts land in a real account with a verifiable tx hash (linked to Stellar Expert in the Payouts table). Payouts use the pending→settle→compensate pattern: a failed transfer refunds the project's reserved allocation and marks the payout `failed`.

## Non-custodial wallet login (Freighter & Albedo)

Investors can sign in with their own Stellar wallet instead of an admin-created custodial account. The app proves wallet ownership with a **SEP-10** challenge/verify handshake — the server never sees a private key.

**Supported wallets (testnet):**
- **[Freighter](https://www.freighter.app/)** — browser extension. The user must install it and set its network to **Test Net**. The app refuses to proceed if Freighter is on mainnet.
- **[Albedo](https://albedo.link/)** — web popup, no installation required.

**How it works:**
1. The user clicks *Connect Freighter / Albedo* on the login screen.
2. The wallet returns its public key; the backend issues a SEP-10 challenge transaction (`GET /api/auth/wallet/challenge`).
3. The wallet signs the challenge (testnet passphrase); the backend verifies the signature (`POST /api/auth/wallet/verify`) and, on success, **finds-or-creates a non-custodial Investor** keyed by that public key and issues the same JWT session the password flow uses.
4. The connected key shows in the header with a **Disconnect** action; the investor dashboard displays the wallet's **live on-chain testnet balance**.

**Enabling it:**
- Set **`SEP10_SERVER_SECRET`** on the backend to a testnet Stellar secret seed (the signing key for challenges). Generate one with:
  ```bash
  node -e "import('stellar-sdk').then(s => console.log(s.Keypair.random().secret()))"
  ```
- Optionally set `SEP10_HOME_DOMAIN` (default `agri-funds.testnet`).
- When `SEP10_SERVER_SECRET` is **unset**, the wallet buttons return "wallet login is not enabled" and the existing admin/custodial flows are completely unaffected.

No frontend env vars are needed — the wallet libraries (`@stellar/freighter-api`, `@albedo-link/intent`) are bundled and lazy-loaded only when the user clicks Connect.

### Wallet-first account creation (MetaMask-style onboarding)

New investors can **create an account starting from their wallet** ("New here? Create an account with your wallet" on the login screen):

1. Connect the wallet and sign a SEP-10 challenge (proof of ownership — no secret key leaves the wallet).
2. Enter a name (email optional). `POST /api/auth/wallet/register` verifies the signed challenge, creates a **non-custodial** Investor (`custodial=false`, `stellarPublicKey` set) + linked `authType='wallet'` user, and issues a JWT.
3. If the wallet is unfunded, the server **Friendbot-funds it on testnet** and returns the new balance. The onboarding screen shows "Wallet funded on testnet", or a **Fund wallet** button (`POST /api/auth/wallet/fund`) when the balance is still 0 (e.g. Friendbot disabled).

Notes:
- **Idempotent** — onboarding a wallet that already has an account returns the existing records (no duplicate, name not overwritten).
- Reuses the same `SEP10_SERVER_SECRET` gate and the wallet-auth rate limiter (`WALLET_AUTH_RATE_LIMIT_MAX`). No secret keys are ever stored.
- Funding is **best-effort**: if Friendbot is disabled (`STELLAR_FRIENDBOT_ENABLED=false`) or unreachable, the account is still created and the UI shows a "fund manually" hint. Testnet-only enforcement is unchanged.

## API (selected)

```
GET  /api/health                     # public; reports DB connectivity
POST /api/auth/login                 { email, password }
GET  /api/auth/me
GET  /api/auth/wallet/challenge      ?account=G…             # SEP-10 challenge (testnet)
POST /api/auth/wallet/verify         { transaction }         # SEP-10 verify → JWT (login)
POST /api/auth/wallet/register       { transaction, name, email? }  # wallet-first account creation + Friendbot fund
POST /api/auth/wallet/fund                                   # Friendbot-fund the caller's own wallet (auth)
GET  /api/events?ticket=…            # SSE stream (ticket from /api/events/ticket)

GET  /api/dashboard
GET  /api/investors
POST /api/investors                  { name, email? }       # admin; Friendbot-funds a testnet wallet
POST /api/transactions/invest        { investorId, amount }
POST /api/transactions/allocate      { projectId, amount }
GET  /api/treasury/overview
POST /api/distributions/generate     { projectId, platformFeePercent?, periodStart?, periodEnd? }

# Institutional Readiness — Commercial (Phase 1)
GET/POST/PATCH /api/buyers           # + /api/buyers/:id/archive, /api/buyers/summary
GET/POST/PATCH /api/offtake          # offtake agreements + /api/offtake/summary
GET/POST/PATCH /api/deliveries       # sales & delivery + /api/deliveries/summary
GET/POST/PATCH /api/invoices         # payment cycles + /api/invoices/summary
```

Write paths that move funds accept an `Idempotency-Key` header so a retried request never double-spends.

Additional API behaviors:

- **Request correlation** — every response carries an `X-Request-Id` header (honoring an inbound one if present); the id also appears in the access log line for tracing.
- **Money/auth rate limits** — money-moving and wallet-auth endpoints are rate-limited (see `MONEY_RATE_LIMIT_MAX` / `WALLET_AUTH_RATE_LIMIT_MAX`); exceeding the limit returns `429`.
- **Distribution periods** — `POST /api/distributions/generate` records a reporting period (`periodStart`/`periodEnd`, defaulting to the current month-to-date). Each `(project, periodStart, periodEnd)` can be generated only once; a repeat returns `409` so a period can't be double-distributed.
- **Opt-in pagination** — list endpoints (`/api/transactions`, `/api/investors`, `/api/payouts`, `/api/distributions`, and the new commercial lists) return the full array by default, or a `{ data, pagination }` envelope when `page`/`limit` query params are supplied.

## Institutional Readiness module (in progress)

A governance/due-diligence layer being built on top of the platform, **without touching** the Stellar/treasury/auth core. **Phase 1 (Commercial) is implemented**: off-chain business records under a new **Commercial** nav section.

- **Buyers** — register offtakers with verification status; summary of active/verified buyers + total contracted volume.
- **Offtake agreements** — buyer commits to purchase a project's crop (quantity × unit price = contract value); summary of contracted revenue, contract utilization %, and remaining commitments.
- **Sales & Delivery** — record harvest deliveries against agreements; delivered-vs-contracted, outstanding deliveries, revenue generated/collected.
- **Payments** — invoice payment-cycle tracking with overdue alerts, average payment cycle (days), and collection rate.

Phase 2 (KPI / yield / investor-confidence dashboards) and Phase 3 (governance approvals + milestone-gated capital release) are planned but not yet built.
